# Architecture

The independent C++20 core will own rules, legality, explicit chance transitions, state invariants and replay. Keep versioned game definitions/data and effect composition separate from native extensions. Unknown mechanics and ambiguous legality fail closed. Rules version, identity mappings, errata and restriction tables are explicit inputs. Do not treat any AI library as rules authority.

Proposed module boundaries:
- core: typed IDs, canonical state/encoding, seed streams, transition and chance contracts.
- rules: versioned state machine, action generation, timing, effects and legality.
- content: rights-reviewed functional definitions, print mappings and behavioral coverage.
- agents: observation-only policies, heuristic/tactical/search baselines, optional learned policy/value.
- research: independent blind discovery, separate meta evaluation, strong-opponent co-evolution and holdout validation.
- matches/tournaments: BO3 policy, observed-information sideboarding, configurable event rules and distinct statistical projections.
- orchestration: Python workers, versioned manifests, atomic checkpoints, resource limits and reporting.

Native workers and Python communicate via versioned contracts; benchmark before committing to a binding or storage technology. The current executable is only a synthetic process probe, not a production protocol. OpenSpiel is optional and replaceable after license review; PyTorch/storage choices require justification. No external dependency is currently integrated. Future-set extension requires versioned legality, effect semantics and regression coverage.

## CTR-0.2 validated foundation
Header-only C++20 generic tagged IDs, explicitly domain-separated mt19937_64 streams seeded using seed_seq(root low/high, domain, run low/high), and rejection sampling for uniform full-width inputs. Version-1 synthetic fixture: three-byte state [version,value,pending] and event [version,kind,payload]. Explicit request/outcome events; validated pure value transitions; replay consumes encoded events without RNG. Prefixes may end pending. These are demonstrator schemas, not game-specific rules or production serialization. No weighted chance or RNG checkpointing yet. Future kernel must separate full state from agent observations and trace every implemented rule to authorized versioned sources and independent tests.

## CTR-1 generic subtask A
Original synthetic two-player fixture separates authoritative State from viewer-specific Observation, with tagged player/entity IDs, four fixed slots and two zones. Trusted observation supplies legal action candidates; authority validates the chosen action against full state before applying a value transition. Synthetic priority transfer, double-pass turn advancement, reveal/reset and terminal handling are fixture-only rules. Projection tests verify hidden-label noninterference, not comprehensive information security. No policy process isolation or production protocol. The manual rule source admission ledger and rule-to-test mapping define provenance/traceability prerequisites for game-specific development. Next generic contracts are ordered event/effect/trigger resolution and bounded loop rejection; no official rules assumed.

## CTR-1 generic subtask B
Version-1 synthetic effect program uses typed credit/debit events, explicit replacement and trigger tables, bounded FIFO processing and value-returning transactions. Rule IDs are unique within each table; ascending IDs determine replacement precedence and trigger ordering independently of registration order. Replacement resolution restarts after each rewrite, rejects repeated events and caps rewrites; cancellation skips mutation and triggers. Only the final applied event can enqueue triggers. Validate all input/rules before processing; enforce balances 0..100 and event/pending/rewrite budgets. All mutations and trace records are local until complete success. In-memory records carry original event, replacement IDs, applied event or cancellation, and trigger IDs. No production timing semantics or serialization; fixture is independent of subtask A. Future integration must preserve observation boundaries and distinguish authoritative traces from agent-facing views.

## CTR-1 generic subtask C
Synthetic integration combines kernel::State and effects::State into a value-returning transaction. Observation includes the existing player projection and both public balances. Cost derives from pre-action own public-slot count; reveal initiates a debit of 3 minus count, replacement 3->2, then a trigger on debit 2 credits the opponent by 1. Both legal reveal paths have final debit 2; the trace distinguishes replacement versus direct debit. Pass has no payment. Legal generation runs the fixed payment cascade from trusted observations, while application independently validates full state, resolves payment locally, applies board transition and validates result. Version-1 canonical state encoding is 26 bytes: version/turn/priority/passed/balances followed by four zone + little-endian 32-bit label records. Four-byte action encoding: version/actor/kind/target. Replay re-executes immutable synthetic rules from encoded initial state and at most 32 encoded actions; no RNG. This is authoritative private data, not an agent interface. No serialized effect trace, production rules identity/digest or general continuous effect framework. Next generic combat-like and scoring/terminal contracts remain independently specified; official source admission is required for real game rules.

## CTR-1 generic subtask D
Standalone synthetic conflict contract uses four fixed slots (two per side), HP and power 1..3, removed units canonicalized to (0,0), and one target/idle order per slot. Validate the entire vector against the pre-round state, aggregate all damage from the immutable snapshot, then mutate a value copy, remove defeated units and increment the opponent's score once per removal. Scores must equal opposing removed-slot counts. At round four or elimination, derive outcome from score comparison including ties. State wire schema v1: 12 bytes (version, round, scores, four hp/power pairs); order schema v1: 5 bytes (version, four targets). Replay validates at most four batches. This is a standalone all-public synthetic fixture, not integrated with the previous effect/action kernel or a model of official combat or scoring.

## CTR-1 generic subtask E
Reusable integer modifier evaluator accepts base 0..100, four-bit active mask and at most 64 immutable rule records. Each rule has globally unique nonzero ID, layer 0..7, required activation mask and bounded set/add/multiply operand. Validate even inactive records, sort by layer then ID, evaluate from base each call and reject out-of-range intermediate values. Mask changes activate or remove modifiers without mutating a cached value. Existing integrated v1 cost uses public slot-derived mask and two additive rules; replacement normalization and replay semantics remain unchanged. Separate variable-price fixture verifies final payment change after replacement/trigger processing. ResourceViolation (derived from invalid_argument) identifies balance overflow/underflow; integrated IllegalAction distinguishes kernel action rejection, invalid state/configuration errors propagate, invariant failure is logic_error. Enumeration filters only ResourceViolation. Future arbitrary-program design must distinguish configuration-caused resource failure from expected unaffordability and provide complete observation validation. No official layering or timing semantics assumed.

## CTR-1 boundary hardening and gate audit
Canonical synthetic observations validate viewer/priority/turn, terminal constraints, sorted unique visible slots, owner/zone consistency, presence of own slots and private counts derived from public slot counts. Opponent private objects cannot occur in a valid projection. Enumeration throws on malformed structure even if non-priority/terminal; direct payment checks valid resources and candidate membership before effects. This does not prove projection authenticity or freshness. Authority-only replay envelope has fixed eight-byte identity and expected final state, verifies identity before bounded v1 replay and compares reconstructed state. No cryptographic integrity or production serialization. Production integration plan and outstanding official acceptance requirements are in CTR1_GATE_AUDIT.md; no new gameplay conventions introduced.

## CTR-1 run identity infrastructure
Python orchestration run_manifest.py produces canonical ASCII JSON version 1 with exactly seven named roles: engine, rules, content, schema, initial, actions and final. For each immutable byte artifact record exact byte length and SHA-256 digest. Sorted keys, compact separators and exact-byte comparison eliminate registration-order differences and reject noncanonical representations; cap manifest at 4096 bytes. Verify the supplied manifest against independently trusted digest, then regenerate from supplied bytes and require equality. No filesystem resolution, network or execution. This is a generic utility; next connect those exact immutable bytes to native replay with bounded parsing. It does not authenticate the trusted digest, prove rules correctness or establish authorization.

## CTR-1 verified native replay
Linux-only authority worker ctr_replay consumes one EOF-delimited binary request: eight identity bytes, 26 initial state bytes, one action count, count x four action bytes, 26 expected final bytes. Fixed overhead 61 bytes, maximum 189 and 32 actions. Reject truncation, count mismatch or trailing input before replay; use existing replay_contract::verify. Exit 0 writes exactly 26 result bytes, 2 means malformed framing, 3 invalid replay, 4 engine/output failure. Python verified_replay.py snapshots the seven immutable artifacts, checks sizes and fixed compatibility markers, verifies the canonical manifest against trusted digest, reads caller-trusted executable up to 32 MiB+1 and requires exact byte match. Executes a private temporary copy, sending only the verified request bytes with five-second timeout, checking status, empty stderr and final bytes. No arbitrary rule/data loading, signature, sandbox or shared-library identity. Captured process output is not capped independently of trusted worker behavior. No production game rules assumed.

## Source-profile admission validator (E0012)
Standalone Python source_admission.py validates a caller-trusted tuple of 1..64 distinct source pins (ID, revision, SHA-256), one review per pin, exact five-dimensional scope (region, format, event, activity, distribution), explicit admitted status, publisher/locator/reviewer/evidence reference, and inclusive effective and review intervals. Reject unknown/missing/extra/duplicate pins or records and altered, empty, mutable or oversized bytes (32 MiB per artifact). Return verified immutable bytes in explicit pin order; no partial success, file or network access. Trust, completeness, precedence and legal determinations remain external obligations. Not connected to native replay or CTest; no official records admitted.

## Generic authoritative object storage (E0018)
include/ctr/object_store.hpp provides validated Snapshot values containing typed object instance and functional type IDs, principal ownership, ordered containers and explicit visibility/count policy. observe emits only permitted contents and configured counts, with container existence and session/revision as public metadata. apply validates exact session/revision, unique object transfers from the original membership, rejects same-container transfers, copies state, retains survivors in order, appends incoming objects in transaction order, increments revision once and revalidates. Bounded size and overflow rejection. No mutation of input on success or failure; public value types, not a persistent immutable store. Trusted authority supplies IDs/viewer/commands; not a legality checker or security sandbox. No serialization, creation/destruction, ownership change or official zone logic. Existing fixture and replay remain separate. E0018 verifies small-state transfer oracle and visibility perturbations.
